The handoffs

This page shows what each stage hands to the next, and why the chain breaks where it does.

An agent can hold a stage when two things are true of it: what the stage is given is an artifact, and what it hands back is an artifact. An artifact is not a conversation, a shared understanding, or a person who happens to know. An artifact has a name. The next stage can read it, and somebody who was not there can check it.

That is harder to meet than it sounds. It is what separates the stages agents already hold from the stages they do not.

The chain

Here is what is actually handed over as one piece of work goes from somebody wanting it to its address being retired. Where the artifact exists, the line names it. Where nothing is handed over yet, the line says missing. Where the artifact is written down but nothing makes it yet, the line says coming.

Source           →  (coming) for each step, an agent or solution that fits, or "build one"
Test             →  the suite, written from the statement before any program
Code             →  the programs, passing the suite, with an account and a run record
Review           →  missing
Security review  →  missing

Six stages are marked missing. Two of them, Review and Security review, are at the front, where a program is read rather than written. The other four are in the back half. The chain now runs without a break from a statement of the job to a package, and has more gaps once the agent is running. Three more links are written down but not yet made.

Test comes before Code, here and on the map. The suite is written from the statement, before any program exists, and the program is written to it. A line that names an artifact means the artifact exists. It does not mean an agent holds the stage. Monitor, for example, has its artifact, made by the platform's own programs, but no agent holds that stage yet. Impact, Source and Acceptance are marked as coming: what each one hands on is settled, but nothing makes it yet.

The Update stage is also changing. A new version will first run as a candidate beside the old one. There it will be checked against its own declaration, and against what each agent or solution that depends on it counts as done. Only then will it be promoted. Update hands on the same agent on the new version, with a record of the candidate run, the checks and the promotion.

Why agents held the middle first

Nobody designed the middle of this lifecycle to be agentic. It became agentic because packaging, release and deployment had already been forced into artifacts for other reasons, decades ago, by people who wanted repeatable builds. A package with a manifest and a digest is an artifact whether or not an agent reads it.

So when agents arrived, four stages already had a defined input and a defined output, and all it took was an agent that could read what was there. That is why agents could hold the stages from Build to Conformance early, and no other stages at first. Those stages were no easier than the rest. Agents could hold them first because each one already had a defined input and output.

What got the front moving

Agents could not hold Code or Test, and the reason was the same for both. Nothing defined went in, and nothing that could be checked came out. A model given a design wrote a program. Another model given the same design wrote a different program. Neither could be compared to anything, because the design was prose and the program was the first artifact in the chain. Then the same author wrote the tests, so the tests encoded whatever the program already did, including its mistakes.

A better model would not have fixed this. What was missing was a statement of what must be true of the program, written before the program existed by something that would not write it. That is what the Test stage now hands over. It is a suite of tests written from the statement of the job, naming the functions the program will have to provide. Before it is handed on, the suite is run with no program present. Every test should fail, which shows that each one really checks something. With the suite in hand, the Code stage has an input, an output and a check its writer does not control. A coding harness can then hold the stage, working the way a coding session works, for as many rounds as it takes. The harness cannot change the tests or the statement.

One more artifact was needed to make the front hold. It is not on the chain, because no stage hands it to the next. It is a prototype: a person's own working version of the thing, made in any tool and any language. Making one is called agentic prototyping. The prototype goes into the Code stage, which reads it as the most exact statement of what was wanted and writes the programs again so they pass the suite. That is called agentic transpiling. Only programs that the Code stage delivers and signs itself leave it, and the Build stage refuses anything else. That rule lets people prototype freely without the prototype becoming the product.

Why review is still stuck

Review and Security review are the two gaps left at the front, and the same thing is missing from both. Everywhere else, a review is already an artifact: a list of findings, each one naming a place and making a claim that can be answered. What nobody has agreed is what a finding is and what it means to answer one. The Code stage now gives a reviewer more to read than it used to: an account of what was written, and a record of how many rounds it took. A reviewer should know when a program took twenty-eight rounds. What is missing is an agreed format for saying so.

Why the back end is stuck

Retract, Eval, Cost and Rollback look like four unrelated problems, but they have one thing in common: each needs an agreement that nobody has written down yet.

Eval needs a standard that was written before the work. Retract needs a rule that only whoever published something may take it down, and a record of every name it published, so it knows what it may remove. Cost needs every amount spent to be traceable to a job. Rollback needs a rule about who may decide, and on what evidence. In each case the machinery is easy to build, and what is missing is the agreement.

Agreements can be written, and this site is a place to write them. Publish is no longer on this list, because its agreement was written: the publisher may write to one folder only, it records every name it places, and it reads every address back before calling it published. Incident response is off the list for the same reason: it was agreed that the agent holding it only keeps the record. It writes a timeline of what is known and marks what is not known as unknown. It does not guess at a cause, and it does not restart anything.

The ledger

Some of what a stage finds is not handed to the next stage at all. A change that breaks something another person's work depends on leaves a debt to that person. A problem found and left unfixed is a debt too, owed to ourselves. The chain has nowhere to put either, so the lifecycle keeps both in a separate record called the ledger.

The ledger holds two kinds of debt under one numbering. Change dependency debt is owed to the owner of something that depends on what changed. It has a deadline, and until it is settled the deployment manager will not promote, roll back or retire the changed agent. Technical debt is owed to ourselves and blocks nothing. Any stage can add an item, and the deployment manager reads the ledger before it acts. The ledger is a platform service rather than an agent, and it is coming.

The loops the chain does not draw

The chain above runs one way, but real work does not. A finding sends the program back to be written again. A failed test does the same, and inside the Code stage that loop runs many times before anything is handed on. A refused conformance check or a poor eval can send the whole thing back to design, and rollback is a reversal by definition. Most of the time anybody spends on software is spent going round one of those loops rather than moving forward along the chain.

The chain is drawn straight anyway, because the question here is what passes between two stages, and that is the same artifact whether it passes for the first time or the fourth. A loop is the same handoff happening again. The difference shows in the record. A stage that has run four times has four results, and somebody has to say which one is current, which a straight line never has to do.

The test for a stage

Three questions settle whether a stage is ready for an agent to hold, and the answer to all three has to be yes.

  • Is the input an artifact? It has to be something with a name that the previous stage actually produces, not something the agent would have to go and ask about.
  • Is the output an artifact? It has to be something the next stage can read without the agent there to explain it.
  • Is there a check the agent does not control? It has to be written before the work, by something other than whatever does the work.

The third question is the one most often skipped, and it is the one that matters most. An agent that writes the program, writes the tests and runs the tests has made a closed loop, and a closed loop always passes. Having the tests written by something other than the program's writer is what opened that loop at the front of this lifecycle.

Passing all three means an agent can safely hold the stage on its own. A person's approval can still be worth having. Deploying, configuring and decommissioning change things in ways that are awkward to undo. When a person says yes to one of them, that yes is a record that a person decided. It is not a check on whether the agent was competent. That record is worth keeping however capable the agent is.

What this is built on

The Build and Release entries describe a manifest, a digest and a signed build record, which is the provenance chain that SLSA and in-toto already specify and Sigstore already implements. Nothing here replaces that work, and a serious implementation should use it. What this site adds is the rest of the lifecycle. It applies the same expectation, a named artifact and an outside check, to the stages where neither existed, and it carries the same provenance chain one stage further back, to the programs themselves.
