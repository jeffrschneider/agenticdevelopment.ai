The handoffs

What passes between stages, and why the chain breaks where it does.

A stage can be held by an agent when two things are true of it: what it is given is an artifact, and what it hands back is an artifact. Not a conversation, not a shared understanding, not a person who knows. Something with a name, that can be read by whoever comes next and checked by somebody who was not there.

This sounds like a low bar and it is not. It is the whole difference between the stages that have moved and the stages that have not.

The chain

Following one piece of work from somebody wanting it to the address being retired, here is what is actually handed over. The links that exist are solid. The links that are missing are marked.

Nine gaps. Four run together at the front, where a program is written and checked, and the other five are spread across the back half: the middle of the lifecycle is joined up and both ends are not.

Why the middle joined up first

Nobody designed the middle of this lifecycle to be agentic. It became agentic because packaging, release and deployment had already been forced into artifacts for other reasons, decades ago, by people who wanted repeatable builds. A package with a manifest and a digest is an artifact whether or not an agent reads it.

So when agents arrived, four stages were already waiting with a defined input and a defined output, and moving them took an agent that could read what was there. That is why Build through Acceptance moved quickly and nothing else did. It was not the easiest work. It was the work that already had a shape.

Why the front end is stuck

Code, Test, Review and Security review are stuck together, and they are stuck for one reason: nothing is handed in and nothing checkable comes out.

A model given a design writes a program. Another model given the same design writes a different program. Neither can be compared to anything, because the design was prose and the program is the first artifact in the chain. Then the same hand writes the tests, so the tests encode whatever the program already does, including its mistakes. Then review, which is the one place this would be caught, has no format for a finding and no rule about answering one, so it falls to a person reading carefully.

The missing piece is not a better model. It is a statement of what the program must be true of, written before the program and by something that is not going to write the program. Everything else in this phase follows from having that.

Why the back end is stuck

Eval, Publish, Cost, Incident response and Rollback look like five unrelated problems and share one shape: each needs something written down that nobody has written down.

Eval needs a standard that predates the work. Publish needs an authority to write to an address and a record of what was written. Cost needs every spend attributable to a job. Incident response needs a way to stop an agent that is still answering. Rollback needs a rule about who may decide and on what evidence. In each case the machinery is easy and the missing thing is an agreement.

That is a more hopeful diagnosis than it sounds. Agreements can be written. This site is a place to write them.

The loops the chain does not draw

The chain above runs one way and real work does not. A finding sends the program back to be written again. A failed test does the same. A refused acceptance or a poor eval can send the whole thing back to design, and rollback is a reversal by definition. Most of the time anybody spends on software is spent going round one of those loops rather than moving forward along the chain.

The chain is drawn straight anyway, because the question here is what passes between two stages, and that is the same artifact whether it is passing for the first time or the fourth. A loop is the same handoff happening again. Where it changes something is in the record: a stage that has run four times has four results, and "which one is current" is a question a straight line never has to answer.

The test for a stage

When considering whether a stage is ready to be held by an agent, three questions settle it, and all three have to be yes.

  • Is the input an artifact? Something with a name that the previous stage actually produces, not a thing the agent would have to go and ask about.
  • Is the output an artifact? Something the next stage can read without the agent being present to explain it.
  • Is there a check the agent does not control? Written before the work, by something other than the thing doing the work.

The third is the one most often skipped, and it is the one that matters. An agent that writes the program, writes the test and runs the test has produced a closed loop, and a closed loop always passes.

Passing all three makes a stage safe to hold without approval. It does not make approval wrong. Some stages keep a person in the loop because the decision is theirs to own rather than because the agent needs watching, and who holds a stage separates the two.

What this is built on

The Build and Release entries describe a manifest, a digest and a signed build record, which is the provenance chain that SLSA and in-toto already specify and Sigstore already implements. Nothing here replaces that work and a serious implementation should use it. What is added is the other end: the same expectation of a named artifact and an outside check applied to the stages where neither exists yet.

The four levels on who holds a stage are a maturity model, and maturity models for software delivery are well-travelled ground. This one is narrow on purpose. It asks one question, who holds this stage, and it is meant to be read stage by stage rather than as a single score for an organization.
