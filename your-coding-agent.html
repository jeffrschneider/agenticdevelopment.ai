The family of standards

Let your coding agent write the whole agent.

The coding agent you already use can write an agent from its spec through its code, in one folder and one context. It does not judge its own work: a check it does not control says what is missing, and a person approves the spec. Claude Code does this with the ADLC plugin, and any other coding agent, such as Codex or Cursor, or a person, can work the same folder from its AGENTS.md.

Install the plugin in Claude Code.

in Claude Code
> /plugin install adlc --marketplace CommonAgent/adlc
> /adlc:start agents/release-notes Reads the pull requests merged since the last release and drafts release notes.

The start lays out a build folder for the new agent, keeps the person's own words in request.md, and begins with the spec. The plugin is open source under Apache-2.0, at CommonAgent/adlc.

Here is how the work moves.

The work has two phases. First your coding agent writes the spec, and the person approves it. Then it builds everything else, in whatever order works best for it, and the check judges the result.

  1. Write the speceach feature with its requirements and acceptance scenarios, what the agent refuses, what it does when it finds nothing, and what it does when a system fails; what only the person can answer is askedyour coding agent, with the person
  2. Approve the spec a personthe person reads the spec in plain words and approves it, and it can't change after thatthe person
  3. Build the agentthe architecture record, the agent's files, the tests and the code, in any order; the check runs every gate over the folder and names what each still needs, and the tests can't change once the code has been judged against themyour coding agent
  4. Open the pull requestonce the build has passed every gate, the folder committed, with every call the coding agent made that the person did notyour coding agent

The roles of the spec writer, the solution architect, the test writer and the code writer all stay. Here one agent does the work of all four, and what keeps the work honest is the check, not a second author.

Run the check after every change.

in the build folder
$ node .adlc/check.mjs
The spec: 2 things missing.
  - the empty case is not stated; say what the agent does when it is given
    nothing to work on or finds nothing
  - the failure case is not stated; say what the agent does when a system it
    reaches fails or answers wrongly

Before the spec is approved, it says what the spec still needs. After that, it runs every gate over the folder at once (the architecture record, the agent's files, the tests and the code) and names what each still needs. It is the reference agents' own checks, carried into the folder unchanged: the spec writer's rules for a spec and for the agent's files, the solution architect's for the record, the test writer's for a suite, the code writer's for the code, and the Common Agent packer. If a file that was already approved changes, the check stops, and only the person, not the coding agent, can send the build back.

Here is what only the person does.

  • Answers what only they can decide. The name, the price, what the agent may reach and spend, and every case their words leave open. The coding agent asks, gives its recommendation, and waits.
  • Approves the spec. node .adlc/approve.mjs is the person's command. In Claude Code a hook stops the coding agent from running it, from editing a file that can't change any more, and from editing the check itself.
  • Sends the build back. node .adlc/approve.mjs --send-back spec opens the spec again, and --send-back build lets the tests change again, when something already settled has to change.

On one machine with no service behind the folder, these are conventions the coding agent could break, because it runs with the person's rights. They become binding when a lifecycle service or a pull request check runs on the same folder.

Here is how the work comes back.

  • A pull request, once the build has passed. Its description lists every call the coding agent made that the person did not.
  • The repository's own check. A pull request check can run the Common Agent packer on the folder and the folder's own check, so the same check runs again where the coding agent can't change it.
  • The stages after the code. Review, Security review and Package read the work as they read anyone's.

The plugin was proven on a holiday checker built from a person's paragraph by a fresh Claude Code session. Where the paragraph said what the agent may reach, the answer quoted it; where it said nothing of what the agent may spend, the coding agent asked and quoted the reply. It reached a pull request the packer accepted. The reference builder, the same plugin run with no person at the keyboard, built a digest of the Hacker News stories about a topic from three messages: the request, the address of the service it reads, and the approval.

Another coding agent works the same folder.

Every build folder carries its instructions as AGENTS.md, which Codex, Cursor and most coding agents read on their own, and CLAUDE.md points to it. A coding agent without the plugin, or a person, follows the same two phases and runs the same check; only the hooks are the plugin's.
