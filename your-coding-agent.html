The family of standards

Let your coding agent write the whole agent.

The coding agent you already use can write an agent from its spec through its code, in one folder and one context. It does not judge its own work: at every stage a check it does not control says what is missing, and a person approves the spec. Claude Code does this with the ADLC plugin, and any other coding agent, such as Codex or Cursor, or a person, can work the same folder from its AGENTS.md.

Install the plugin in Claude Code.

in Claude Code
> /plugin install adlc --marketplace CommonAgent/adlc
> /adlc:start agents/release-notes Reads the pull requests merged since the last release and drafts release notes.

The start lays out a build folder for the new agent, keeps the person's own words in request.md, and begins at Requirements. The plugin is open source under Apache-2.0, at CommonAgent/adlc.

Here is how the work moves.

Your coding agent writes every stage, in this order. Each stage passes when its check does, and what it settled is pinned, so a later stage never moves it.

  1. Write the speceach feature with its requirements and acceptance scenarios, what the agent refuses, what it does when it finds nothing, and what it does when a system fails; what only the person can answer is askedyour coding agent, with the person
  2. Approve the spec a personthe person reads the spec in plain words and approves it, and it is pinnedthe person
  3. Write the architecturethe systems the agent stands on and each decision with its reason; the record is written from them by the solution architect's own codeyour coding agent
  4. Write the agent's filesthe words of the declaration; the files are generated from the spec and the record, and the Common Agent packer must accept themyour coding agent
  5. Write the suitea test for every acceptance scenario, each named for what it checks, shown to fail against empty scriptsyour coding agent
  6. Write the scriptsthe code, until the suite passes, each script is noticed when it is blanked, and the packer accepts the folderyour coding agent
  7. Open the pull requestthe folder committed, with every call the coding agent made that the person did notyour coding agent

The roles of the spec writer, the solution architect, the test writer and the code writer all stay. Here one holder holds them, and what keeps them honest is the check, not a separate author.

Run the check after every change.

in the build folder
$ node .adlc/check.mjs
Requirements: 2 things missing.
  - the empty case is not stated; say what the agent does when it is given
    nothing to work on or finds nothing
  - the failure case is not stated; say what the agent does when a system it
    reaches fails or answers wrongly

It names the stage the folder is at and what is missing there, and nothing else. It is the reference agents' own checks, carried into the folder unchanged: the spec writer's rules for a spec and for the agent's files, the solution architect's for the record, the test writer's for a suite, the code writer's for the code, and the Common Agent packer. A pinned file that changed stops it, and the person, not the coding agent, sends the build back to the stage that wrote it.

Here is what only the person does.

  • Answers what only they can decide. The name, the price, what the agent may reach and spend, and every case their words leave open. The coding agent asks, gives its recommendation, and waits.
  • Approves the spec. node .adlc/approve.mjs is the person's command. In Claude Code a hook stops the coding agent from running it, or from editing a pinned file or the check.
  • Sends the build back. node .adlc/approve.mjs --send-back <stage> opens that stage and every one after it again, when something it settled has to change.

On one machine with no service behind the folder, these are conventions the coding agent could break, because it runs with the person's rights. They become binding when a lifecycle service or a pull request check holds the same folder.

Here is how the work comes back.

  • A pull request, once every stage has passed. Its description lists every call the coding agent made that the person did not.
  • The repository's own check. A pull request check can run the Common Agent packer on the folder and the folder's own check, so the gate is the same one the coding agent ran, held where the coding agent cannot change it.
  • The stages after the code. Review, Security review and Package read the work as they read anyone's.

The plugin was proven on two agents built from a person's request by a fresh Claude Code session: a digest of the Hacker News stories about a topic, and a release-notes writer that reaches a code host, a team chat and a model. Each reached a pull request the packer accepted, and each stopped where only the person could decide.

Another coding agent works the same folder.

Every build folder carries its instructions as AGENTS.md, which Codex, Cursor and most coding agents read on their own, and CLAUDE.md points to it. A coding agent without the plugin, or a person, follows the same stages and runs the same check; only the hooks are the plugin's.
