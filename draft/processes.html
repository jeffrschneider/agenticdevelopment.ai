The family of standards

A process is a lifecycle you can actually run.

A map of stages says what ought to happen. A process says who holds each step, what they're handed, what they give back, and what to do when a step goes wrong. Here are three examples to copy. Put your own holders in them and run them.

Each one is written in the open Agent Processes format, so an orchestrator can read it and run it. A process document names the phases in order, the agent or person who holds each one, the file that passes at every handoff, the ways a phase can send the work backwards, the rules that stay true whatever happens, and what's worth measuring afterwards.

Steps a person holds have a dashed edge. The package step is marked as the on-ramp, as it is everywhere on this site: it's where your work becomes an Agent Package, the easy way onto the mesh.

Make a new agent

A request in words becomes a running agent. Nine steps: the owner says yes at three gates, and agents of the lifecycle hold the rest. The spec step settles four things before any shape is drawn, and two of those can end the run before anything gets built. Five named deviations send the work backwards, because the spec you approve is rarely the spec you first read.

  1. Write the specthe four answers settled and the spec draftedspec writer, with the owner
  2. Approve the specthe owner answers what is open and says yesthe owner
  3. Write the suitetests from the spec alone, shown to fail against nothingtest writer
  4. Write the scriptsthe scripts the spec names, passing the suitecode writer
  5. Make the package on-rampa signed package from the spec and the scripts onlypackage maker
  6. Approve the deploythe owner reads the package's record and says yesthe owner
  7. Deploy the agentthe package installed, or the running agent updateddeployment manager
  8. Check conformancethe package's own declarations tested on the agentconformance checker
  9. Publish the agentthe owner reads the AgentDoc and says it may be listedthe owner

There's no separate process for changing an agent. A change is this process run again, with the change in words and the running version attached as the prototype.

Record an incident

An agent goes quiet, or a job fails. The process builds a timeline of what's known from the platform's records and the agent's own, says where every fact came from, and marks the gaps as gaps. It never guesses a cause and never proposes a fix. Deciding what to do stays with a person.

  1. Notice the failurethe quiet agent or failed job, and the timewatcher, or a person
  2. Gather the recordsthe platform's and the agent's records, attachedthe incident owner
  3. Record the incidenta timeline naming every fact's source and every gapincident recorder
  4. Decide what happensleave it, restart it, retire it, or change itthe incident owner

Retire an agent

Stopping an agent is easy. Retiring one takes more care: the address has to stop answering without breaking whatever pointed at it, the records have to outlive the thing they describe, and somebody has to decide whether the name is released or held. This process says who decides each of those, and in what order.

  1. Say what goesthe agent, the reason, and who must be told firstthe owner
  2. Retract the listingthe agent's listing taken out of the catalogthe owner
  3. Approve the removalthe owner reads what will be removed and says yesthe owner
  4. Remove the agentthe deployment manager instructed to remove it allthe owner and the deployment manager
  5. Close the AgentDocthe AgentDoc marked retired, with date and reasonthe owner

You can write a process for any stage.

A stage is ready for a process when what it's given and what it hands back are both artifacts. The handoffs page shows what passes at each one, and the stages page names the role that holds it.
