The family of standards

A handoff is something you can hold.

An agent can hold a stage when what it's given and what it hands back are both artifacts: things with a name that the next stage can read, and that somebody who wasn't there can check. A conversation doesn't count. Neither does a person who happens to know.

Here is what each stage hands to the next.

One piece of work, from somebody wanting it to its address being retired. Each line names the artifact that stage hands on. Open any stage for what it's given and how you can tell it's done.

  1. Define
  2. Requirementsa statement of the job, and the questions it couldn't settle
  3. Designthe shape: the steps, and program or judgment on each
  4. Impactthe impact report: each dependent, and what the change does to it
  5. Sourcefor each step, an agent or solution that fits, or "build one"
  6. Make
  7. Testthe suite, written from the statement before any program
  8. Codethe programs, passing the suite, with an account and a record of every round
  9. Reviewfindings, each naming a place, a claim and a consequence
  10. Security reviewwhat it may reach, what it may spend, and what it must never do
  11. Ship
  12. Package on-rampthe package: declaration (agent-descriptor.json and agent-runtime-requirements.json), parts, manifest, digest
  13. Release on-rampa signed build record, and the package at an address
  14. Deploy goes livea running agent with identity, address and inbox; credentials placed by name and ceilings set before it starts; a signed deployment record
  15. Prove
  16. Conformancea signed verdict against the declaration
  17. Acceptancethe requester's recorded yes, against "done"
  18. Use
  19. Docsa document assembled from the declaration, every claim traceable
  20. Publishan address a person can open, and the digest of what's there
  21. Retracta record of what was taken down, by whom, and when
  22. Run
  23. Monitorwhether each agent is alive, measured by an answer
  24. Evala graded judgment, against a standard set beforehand
  25. Incident responsea timeline of what's known, with each gap marked
  26. Costwhat was spent, by whom, against what was allowed
  27. Change
  28. Updatethe same agent on a new version, proven first, difference recorded
  29. Reconfigurethe same agent on the same version, with changed settings, credentials or ceilings, and a signed record of what changed
  30. Rollbackthe same agent on the version before, and why
  31. Decommissionnothing running, records kept, address retired

Package and Release are the on-ramp: where your work becomes an Agent Package, the easy way onto the mesh. Deploy is where it goes live, with its credentials placed and its limits set before it starts. There's never a moment when the agent is live without them.

Test comes before Code, here and on the map. The suite is written from the statement before any program exists, and the program is written to it.

Update hands on the same agent on its new version, after a candidate run beside the old one. There it's checked against its own declaration, and against what each agent or solution that depends on it counts as done. Only then is it promoted, with a record of the candidate run, the checks and the promotion.

The middle went first because it was already made of artifacts.

The middle of this lifecycle wasn't designed to be agentic. Packaging, release and deployment were forced into artifacts decades ago by people who wanted repeatable builds. A package with a manifest and a digest is an artifact whether or not an agent ever reads it.

So when agents arrived, the stages from Package to Conformance already had a defined input and a defined output, and all it took was an agent that could read what was there. Those stages were no easier than the rest. They were just ready.

The front moved once the tests came first.

Code and Test were stuck for the same reason. Nothing defined went in, and nothing checkable came out. Give a model a design and it writes a program. Give another model the same design and it writes a different one. Neither can be compared to anything, because the design is prose and the program is the first artifact in the chain. Then the same author writes the tests, so the tests faithfully encode whatever the program does, mistakes included.

A smarter model wouldn't fix that. What was missing was a statement of what must be true of the program, written before the program existed, by something that wouldn't write it. That's what the Test stage hands over: a suite written from the statement of the job, naming the functions the program will have to provide. Before it's handed on, the suite runs with no program present, and every test should fail, which shows each one really checks something. With the suite in hand, the Code stage has an input, an output, and a check its writer doesn't control. A coding harness can hold the stage for as many rounds as it takes, and it can't touch the tests or the statement.

One more thing made the front hold, and it isn't on the chain because no stage hands it to the next: the prototype. It's a person's own working version of the thing, made in any tool and any language. Making one is agentic prototyping. The prototype goes into the Code stage, which reads it as the most exact statement of what was wanted and writes the programs again so they pass the suite. That's agentic transpiling. What leaves Code is the rewrite, so people can prototype freely without the prototype quietly turning into the product.

Some stages need an agreement before an agent can hold them.

For these stages, the machinery is easy to build. What each one needs first is an agreement, written down:

  • Review and Security review need an agreed shape for a finding, and for what it means to answer one. A reviewer should also be told when a program took twenty-eight rounds.
  • Eval needs a standard written before the work, by somebody other than the maker.
  • Retract needs a rule that only whoever published something may take it down, and a record of every name it published.
  • Cost needs every amount spent to trace back to a job.
  • Rollback needs a rule about who may decide, on what evidence, and how fast.

Agreements can be written, and this site is a place to write them. Publish shows how it goes: its agreement says the publisher writes to one folder only, records every name it places, and reads every address back before calling it published. Incident response works the same way: the agent holding it only keeps the record. It writes a timeline of what's known, marks what isn't known as unknown, never guesses a cause, and never restarts anything.

Debts go in the ledger, not the chain.

Some of what a stage finds isn't handed to the next stage at all. A change that breaks something another person's work depends on leaves a debt to that person. A problem found and left unfixed is a debt too, owed to ourselves. The chain has nowhere to put either, so the lifecycle keeps both in a separate record, the ledger.

Change dependency debt has a deadline, and until it's settled the deployment manager won't promote, roll back or retire the changed agent. Technical debt blocks nothing. Any stage can add an item, and the deployment manager reads the ledger before it acts. The platform keeps the ledger; it isn't an agent, so it has no role.

The chain is drawn straight, but real work goes in loops.

A finding sends the program back to be written again. A failed test does the same, and inside the Code stage that loop runs many times before anything is handed on. A refused conformance check or a poor eval can send the whole thing back to design, and rollback is a reversal by definition. Most of the time anybody spends on software is spent going round one of those loops.

The chain is still drawn straight, because the question here is what passes between two stages, and that's the same artifact whether it passes for the first time or the fourth. The difference shows in the record. A stage that ran four times has four results, and somebody has to say which one is current.

Three questions decide whether an agent can hold a stage.

All three have to be yes.

  • Is the input an artifact?Something with a name that the previous stage actually produces, not something the agent would have to go and ask about.
  • Is the output an artifact?Something the next stage can read without the agent there to explain it.
  • Is there a check the agent doesn't control?Written before the work, by something other than whatever does the work.

The third question is the one most often skipped, and the one that matters most. An agent that writes the program, writes the tests and runs the tests has built a closed loop, and a closed loop always passes. Having the tests written by something other than the program's writer is what opened that loop at the front of this lifecycle.

Passing all three means an agent can safely hold the stage on its own. A person's approval can still be worth having. Deploying, reconfiguring and decommissioning change things in ways that are awkward to undo. When a person says yes to one of them, that yes is a record that a person decided, not a check on whether the agent was competent, and it's worth keeping however capable the agent is.

It builds on SLSA, in-toto and Sigstore.

The Package and Release stages describe a manifest, a digest and a signed build record, which is the provenance chain SLSA and in-toto specify and Sigstore implements. Nothing here replaces that work, and a serious implementation should use it. What this site adds is the rest of the lifecycle: the same expectation of a named artifact and an outside check, applied to the stages where neither existed, and the same provenance chain carried one stage further back, to the programs themselves.
