The words this lifecycle uses, and what each one means.

Every page here, the reference agents and the lifecycle API use these words the same way. When two pages seem to disagree, this page settles it.

The lifecycle

Lifecycle
The Agent Development Lifecycle (ADLC): the ordinary software lifecycle, written for work that agents do. The reference has twenty-four stages. An organization's own lifecycle is the reference tailored to its work.
Stage
One of the steps of the lifecycle, such as Requirements, Test, Code, Deploy or Monitor. Each stage names the role that carries it out, what it is given, what it hands back, and when it is done. All twenty-four are on The stages.
Phase
A group of stages that belong together: Define, Make, Ship, Prove, Use, Run and Change. Define holds Requirements, Architecture and Design, Impact and Source. A phase lays the stages out on the map; it does no work of its own.
Tailoring
Shaping the reference to an organization: choosing which stages its lifecycle uses, adding stages of its own, and choosing who holds each role. A stage an organization adds, such as a legal review, is written the same way as the reference stages: its role, what it is given, what it hands back and when it is done. An organization has one lifecycle, and a project can differ from it.

Who does the work

Role
The job that carries out a stage: what anyone holding it must take in, hand back and never do. Roles are written down at agentroles.ai. One role can carry out several stages: the deployment manager carries out Deploy, Update, Reconfigure, Rollback and Decommission.
Holder
Whoever fills a role for an organization: a reference agent, the organization's own agent, a supplier's agent, a person, or an outside tool whose evidence is read. The stage stays the same whoever holds it.
Reference agent
An open source agent that holds a role, published under Apache-2.0 at github.com/CommonAgent/adlc. Run it, read it, or replace it with any agent that holds the same role.
Gate
A point where the lifecycle waits for a person's yes: approving the spec, giving the OK on the code, approving the install, accepting the result. The stages marks each stage that has one.

What passes between stages

Hands back
What a stage gives the next one: always a written artifact, such as a spec, a suite or a signed record, never a conversation. The next stage can start the moment it arrives. The chain is on The handoffs.
Done when
The test that says a stage is finished, written so that someone who did not do the work can check it.
Asset
A record a stage leaves behind that outlives the build: the spec, the suite, the signed build record, the attestations. Which are required is on The assets.
Agent Package
The one thing every lifecycle must end in: the agent's declaration of what it does and refuses, its parts, a manifest and a digest, in the open format at commonagent.net. A platform that installs agents checks the package, not the path that made it.

Running it

Build
One pass through the lifecycle that makes one version of an agent or a process. A build keeps the lifecycle and the holders that were in effect when it started, so a later change to the lifecycle does not change a build already under way.
Process
A lifecycle written so it can be run: who holds each step, what passes between them, and what happens when a step goes wrong. Processes are written in the open Agent Processes format. Examples are on The processes.
Step
One piece of work in a process, held by one holder. A stage can take more than one step: Requirements is writing the spec, then approving it. The Agent Processes format lists a process's steps under the heading phases; on this site a phase is always a group of stages.
Orchestrator
Software that runs a process: it sends each step to its holder, waits at each gate, and records what came back.
Lifecycle API
What any service that runs the lifecycle answers, so a console or another tool can read a build and act at its gates. It is on The API.
