The family of standards

Here are all twenty-five stages.

They run in seven phases, from the first idea to the last day. Each card says who holds the stage, what it's given, what it hands back, and how you know it's done. Keep what you need.

  • Define
  • Make
  • Ship
  • Prove
  • Use
  • Run
  • Change

Reverse engineering is numbered 00, so the other twenty-four keep their numbers. It runs only when needed: when you take on code that already exists, or when the code changed outside the lifecycle.

Retract and Rollback name their roles; the reference publisher and deployment-manager agents don't hold them.

A service that runs these stages reports each build by them, one entry per stage, through the lifecycle API.

What each stage's gate must require, for each tier of risk, is set by an organization's policy, as laid out in the Agentic Governance Framework.

Define

Reverse engineering

00role: reverse engineer

Nobody can decide what to keep until somebody says what's there. It describes what the code is, never whether it's right, and writes no tests; the person decides at Requirements, and on drift each changed behavior goes there to be approved, flagged as a bug for the backlog, or dropped. A codebase that lives fully inside the lifecycle never needs it again, because its forward artifacts are already the truth, so it never runs by routine.

Role
reverse engineer
Given
an existing codebase at a named commit, and its running form if there is one, on either of two triggers: adoption, when the codebase is taken on; or drift, when the code changed outside the lifecycle (hand edits, another team, a vendor drop), seen when its commit differs from the last one any build knew, and then also the last as-built record
Hands back
the as-built record, tied to its source (the repository, the commit digest, and whether the code was only read or also run), in five parts, and on drift only what changed since the last record:
  • behaviors: each thing the code does (its inputs, outputs, refusals and the error handling actually present), each evidenced by a file and line or an observed run, drafted in the feature list's shape (id, name, does, offering) and marked as built
  • architecture as built: the parts, entry points, data stores, systems and networks reached, settings and credentials read, and how it starts and runs, in the architecture standard's record shape, marked as built
  • interfaces: the APIs, commands, messages and file formats, with schemas where they can be derived, in existing formats (OpenAPI, JSON Schema)
  • dependencies: a software bill of materials (SBOM) in CycloneDX or SPDX
  • existing tests and gaps: the tests it already has, what they cover, one baseline run's results, and what couldn't be determined (unreachable code, behavior seen only at run time, anything unclear), each marked
Done when
every claim names its evidence, every gap is marked, and nothing is inferred beyond the evidence

Requirements

01spec-writersolution-planner

Whoever builds and tests from it can't ask what you meant, so it says what the product must do and how anyone can tell that it does, and never invents a name, a price or a permission.

Role
spec writer for an agent; solution planner for a solution
Given
somebody's account of what they want, with whatever they have; where code already exists, or where a build starts from the as-built record of code kept elsewhere, the as-built record, each behavior in which the person approves, flags as a bug for the backlog, or drops
Hands back
the spec (spec-v1): the analysis of the product's functional requirements and capabilities:
  • each feature, with its requirements (each a statement with shall, its kind, the exact words, patterns and numbers it fixes, its source and how it is verified), its inputs and outputs with their schemas, and acceptance criteria as Gherkin scenarios
  • the interfaces it presents, and which must be kept exactly
  • constraints on the whole product: time, size, cost, runtime, security and data
  • the systems it reaches or names, and its settings
  • the open questions only the person can settle
Done when
every feature has requirements and at least one acceptance scenario a test can check; every requirement comes from what the person said, or from a behavior the as-built record found, and nothing still open was made up; every requirement is covered by a scenario; the spec says what the agent refuses, what it does when it has nothing to work on, and what it does when a system it uses fails; and the person has approved the spec

Architecture and Design

02role: solution architectspec-writersolution-planner

The systems named here become the package's runtime requirements, and the bindings are what Deploy places.

Architecture

Role
solution architect, or a person
Given
the spec, and the organization's stack; where code already exists, the architecture as built (part 2 of the as-built record)
Hands back
an architecture record:
  • the systems the agent reaches, in plain words (database, files, text reasoning, mail sender)
  • the product bound to each in dev, test and production: the organization's stack first, a platform default for the rest
  • dependencies on other agents and services
  • the agent's kind: a harness reading skills, code that speaks the network itself, or a container
  • limits on cost, speed, data and trust
  • each decision, with its reason

Design

Role
spec writer for an agent; solution planner for a solution
Given
the spec, and the architecture record
Hands back
the steps, what each is given and hands back, and whether each is a program or a judgment; for an agent, the agent's own files a package is built from (its descriptor, runtime requirements, plugin manifest and a SKILL.md per skill), made from the spec and the architecture record
Done when
every system is named, with the product behind it chosen for each environment the agent will run in; every decision has a reason; every design step uses only the systems the architecture named; the architecture record is the one the architect's own code writes from the facts and the person's answers, and the spec and the record use the same name for each system; and the agent's own files are the ones the generators write from the spec, the record and their wording, and the Common Agent packer accepts them

Impact

03role: impact analyst

Role
impact analyst
Given
the change, the running version, and what depends on it; where code already exists, the architecture as built and the dependencies (parts 2 and 4 of the as-built record)

Done when

Make

Test

05test-writer

Tests come before the program, from the spec, so a test can't pass by agreeing with a mistake. (Yes, people argue about this.)

Role
test writer
Given
the spec, and the agent's own files from Design; where code already exists, the behaviors and the existing tests and gaps (parts 1 and 5 of the as-built record), from which it writes characterization tests that pin today's behavior until Requirements says otherwise; where a build starts from the as-built record of code kept elsewhere, the same parts and the interfaces (part 3), from which it writes tests that pin each behavior the person approved, for code written fresh
Hands back
the suite, with at least one test for each acceptance scenario of the spec, named by its id, and what no test could be written for
Done when
every acceptance scenario has a test; every exact word, pattern and number that a test-verified requirement sets is checked by a test; the tests fail while the programs are still empty, and fail when any one program is removed; every test is named for an approved scenario, requirement or constraint; and no test fails because of a mistake in the test itself

Code

06code-writer

Any code writer can hold it; your prototype is read as the spec and written again against the suite.

Role
code writer: the reference agent, your own coding agent, or a person
Given
the spec, the agent's own files, the suite, and a prototype if there is one, as a build folder on a branch with a "Write the scripts" pull request
Hands back
the programs, an account of what was written, and a record of every round
Done when
all the tests pass, removing any one program makes a test fail, and the tests, the spec and the agent's own files have not changed; every script the agent's files name is written, the scripts read only the settings the agent's files declare, and the Common Agent packer accepts the folder with its scripts

The hand-off. The folder carries its instructions in AGENTS.md and a record of which files may not change, so the coding agent you already use can write this stage, or every stage from Requirements to Code. Either way, its work is checked by something it can't change: the pull request's checks, then the owner's OK. Start here with your own coding agent.

Security review

08role: security reviewer

The blast radius is set before the credentials are given, not after.

Role
security reviewer
Given
the architecture record and the design, the programs, and everything the package will ask for; where code already exists, the architecture as built and the dependencies (parts 2 and 4 of the as-built record)
Hands back
what it may reach, what it may spend, what it must never do, and the reason for each
Done when
every permission asked for has a recorded reason

Deploy

11goes livedeployment-manager

There's never a moment when the agent is live without its credentials and limits; secrets are named, never carried.

Role
deployment manager
Given
the package, where it goes, and the owner's answers as names and numbers
Hands back

Conformance

12conformance-checker

It checks the agent keeps its promises, not that the promises were right; that's Eval.

Role
conformance checker
Given
the package, the agent's address, and its records
Hands back
a signed verdict, case by case, and an attestation: one signed statement, for this version, of which checks on a published check list it passed
Done when
every case from the declaration ran, the verdict is signed, and the attestation names the version, the check list and who attested

Acceptance

13a person

Only the person who asked can say it's what they wanted.

Role
the requester, the person who asked
Given
what was delivered, and "done" as written at Requirements
Hands back
a recorded yes against "done", or a no that says what's missing
Done when
the answer is recorded with who and when, and the request closes

Role
deployment manager
Given
the agent, and the version before
Hands back
the agent back on that version, why, and what can't be undone
Done when

Beside the stages

The ledger

kept by the platform

Debts a change leaves behind: owed to someone who depends on it, or to the agent's own team. An open dependency debt blocks promote and retire; a rollback is allowed and recorded.
