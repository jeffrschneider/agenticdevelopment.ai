The family of standards

Any service that runs the lifecycle answers the same API.

A person may build agents on more than one service, and should be able to follow every build in one place. So a service that implements the lifecycle reports each build stage by stage, in one shape, and says what the person may do next. A client shows what the service says and holds no lifecycle logic of its own.

The schema: lifecycle-api.schema.json · The check: lifecycle-api-check.mjs · Version 0.3

Every service answers these paths.

They sit under /v1/lifecycle on the service. Every request and answer is JSON, and every time is ISO 8601 with a zone.

CallWhat it answers
GET /mewho the key belongs to, { account: { email, name } }, and the service's name, { service: { name } }
GET /buildsthe person's builds, each with its id, name, what it does, its version, what it makes (kind: agent or process), the stage it is at and its state there, where it ended in words, and when it last changed; archived builds only when the request adds ?archived=1
POST /buildsa new build, started from the person's words: does, and kind when it is a process, and if they like refuses, more, name, a prototype repository and the project it is for
GET /builds/{id}one build, stage by stage, with its log and the actions it offers now
GET /builds/{id}/timelinehow long each step took: one bar per step per round, with who held it, whether an agent was working or it waited on a person or on something outside, its start, end and duration, and the totals
GET /builds/{id}/files?path=the bytes of a file a stage handed back, at the link the build gives
POST /builds/{id}/actions/{name}the build after the person takes one of the actions it offered
POST /builds/{id}/trythe answer to one input, sent to the pull request or to the installed agent
GET /builds/{id}/triesthe tries made on the build, newest first
POST /builds/{id}/tries/{tid}/keepthe try, now kept as a new test in the agent's suite
POST /builds/{id}/tries/{tid}/wrongthe try, now sent back to whoever holds the code
POST /builds/{id}/evidencethe build, after a holder outside the service hands back evidence for a stage in one of the open formats
GET /stagesevery stage, in order, and whether the organization's lifecycle uses it; with ?project=, as a build for that project would see it
PUT /stages/{stage}the stages, after the organization (or one project) chooses to use a stage or leave it out
DELETE /stages/{stage}the stages, after a choice is removed, so the stage falls back to the organization's choice, then to used
GET /rolesevery role, and who holds it now; with ?project=, as a build for that project would see it
PUT /roles/{role}the roles, after the organization (or one project) binds a role to a holder
DELETE /roles/{role}the roles, after a binding is removed, so the role falls back to the organization's binding, then to the service's own agent, then to nobody

The person's own key signs every call.

Each call carries Authorization: Bearer <key>. The key is one the person makes for their own account, and the service says how to make one and what it must allow. A client asks for the key once and never sees a password. It sends the key only to the service, and asks for a new one when the service answers 401 or 403.

A build lists all twenty-four stages.

The answer to GET /builds/{id} lists every stage of the lifecycle once, by the ids in stages.json. A stage the service does not run is listed as not_offered, so a client always draws the whole lifecycle and the person can see what this service leaves to someone else.

FieldWhat it says
statenot_started, working, waiting_on_you (the person's act is next), done, refused, stopped, not_offered (this service cannot hand the stage to anyone), not_bound (nobody holds its role), not_applicable (it does not apply to this kind of build, such as Review on a process) or not_used (the build's lifecycle leaves it out)
holderwho holds the stage: a reference_agent (the service's own), your_agent (one the organization brought), a contracted supplier's agent, a person or an outside_tool, with a name, and a handle when it is an agent on the mesh; null for a stage that is not offered, not bound, not applicable or not used
roundseach time the stage ran, newest first; back is true when that round sent the work back
handed_backwhat the stage handed back, in words and as files, each with its size in bytes and a link read with the same key
done_when_metwhether the stage's "done when" was met: true, false, or null while it is not known
wherewhere the work is when the person can open it, such as a pull request with its newest commit and its check; otherwise null
evidencewhat a holder outside the service handed back for the stage, each piece with its format, name, when it arrived, and what the service read in it, in words

Beside the stages, a build carries its id, name, what it does, its version, the handle it answers at once installed, its own log, its actions, and can_try, which says whether a try may be sent now to the pull request and to the installed agent. It also carries kind, agent or process, absent meaning agent, and a service that does not build the kind asked for refuses the request and says so; summary, where it ended or where it is in the words a person reads first, such as "Installed · conforms" or "Stopped at Requirements"; paused, since when and why the installed agent is paused, for example after a conformance check it failed, or null; archived, true once the person archived it; timeline, the same bars the timeline call answers; project, the project it was started under, when one was named; and lifecycle, whose choice of stages it started under and when, { project, at }, with project null when the build named none.

An organization chooses which stages its lifecycle uses.

Not every organization runs all twenty-four stages. It can leave a stage out for the whole organization, or for one project, and a project's choice wins for builds started under that project. When nothing is chosen, every stage is used. GET /stages lists every stage in the order of stages.json, each saying whether it is used, where that choice comes from, and whether this service can run its builds without it.

two stages, as GET /stages?project=billing answers them
{
  "project": "billing",
  "stages": [
    { "stage": "impact", "name": "Impact", "phase": "define",
      "roles": ["impact-analyst"],
      "used": false, "from": "org",
      "can_leave_out": true },
    { "stage": "code", "name": "Code", "phase": "make",
      "roles": ["code-writer"],
      "used": true, "from": "default",
      "can_leave_out": false,
      "why_not": "Code is written to Test's suite; this service cannot build without it." }
  ],
  "updated_at": "2026-11-08T16:40:00Z"
}
FieldWhat it says
projectthe project asked about, or null for the organization
usedwhether the lifecycle uses the stage
fromwhere the choice comes from: project, org, or default, which uses every stage
can_leave_outwhether this service can run its builds without the stage; a fact about the service, not a rule of the organization's
why_notwhen the stage cannot be left out, what needs it, in words a person reads
rolesthe roles that hold the stage; who holds each one is in the roles answer
updated_atwhen a choice this answer reads was last changed; absent when nobody has chosen

PUT /stages/{stage} with { used } makes the choice, and DELETE /stages/{stage} removes it; either takes ?project= for one project, and both answer with the stages as they now stand. The service answers 400 for a stage stages.json does not name, or for used: false on a stage it cannot build without; 403 for a member who is not an admin of the organization; and 409 when the choice could not be saved.

A build keeps the choice in effect when it started. Leaving a stage out later changes the builds started later, never one already running. Each stage the build leaves out is listed as not_used, with no holder, no runs and no actions, and its given says whose choice it was. When a stage both does not apply to the kind of build and is left out, it reads not_applicable; otherwise not_used comes before every other state.

An organization chooses who holds each role.

Each stage is held by one or more roles, the ones written down at agentroles.ai. GET /roles lists every role in stages.json with its contract, the offering an agent holding it answers (role-<id>), its stages, the binding in effect, and where that comes from: project, org, default (the service's own agent) or unbound. PUT /roles/{role} with { holder } binds a role, and DELETE /roles/{role} removes the binding; either takes ?project=. The requester, who holds Acceptance, is always the person who asked.

An agent bound to a role is sent the stage's input under the role's offering, and its answer is the stage's asset, as the service's own agent's would be. The service never calls a vendor's API. A holder outside the mesh hands its evidence back with POST /builds/{id}/evidence in an open format stages.json lists: SARIF, CycloneDX, SPDX, SLSA provenance, in-toto, OpenTelemetry traces with gen_ai attributes, or Pact. The service reads it and shows it on the stage.

A client draws one button for each action, and nothing else.

Every build carries the actions the person may take now. A client shows each one as a button with its label, asks for the inputs it needs, and posts them to /builds/{id}/actions/{name}. It never adds a button the service did not offer and never decides on its own what comes next, so every judgment stays with the service and its agents. When the service offers nothing, the person has nothing to do.

an action, as the build offers it
{
  "stage": "requirements",
  "name": "approve",
  "label": "Approve the spec",
  "needs": [
    { "name": "repository",
      "label": "Your coding agent's repository, as owner/name",
      "kind": "repository",
      "optional": true }
  ]
}

A need's kind is text for a line, words for a paragraph, or repository for owner/name. A need marked optional may be left empty, and is then not sent. An action names the stage it acts at, and that is always a stage the build offers. The answer is the build as it now stands.

Try it, keep what it got right, and send back what it got wrong.

Before the person accepts the code, and after the agent is installed, they can send it one input and read the answer.

  • Try. POST /builds/{id}/try with { say, against }, where against is pull_request or installed. The answer is { try: { id, say, against, answer, ms, at } }. Against the pull request, the service runs the newest commit on that one input, through the same checks its gate uses. Against the installed agent, it sends the agent a message as the person and waits for the reply.
  • Keep. POST /builds/{id}/tries/{tid}/keep adds the try to the agent's suite as a new test file, so the answer it gave becomes one it must keep giving.
  • Wrong. POST /builds/{id}/tries/{tid}/wrong with an optional { why } sends the try back to whoever holds the code, as a comment on the pull request.

GET /builds/{id}/tries lists every try, newest first, each saying whether it was kept and whether it was sent_back. A service may cap how many tries a build has in a day.

An error is words a person can read.

Any refusal is a 4xx or 5xx status with { error } in words, which a client shows as they are. A refused action also carries the build as it now stands. A 401 or 403 means the key is missing, wrong, or does not allow the call. A 429 means the service was asked too often, and a client waits before asking again.

Version 0.3 grows only by adding.

This is version 0.3, served on the /v1/lifecycle path. It changes only by adding. A service never removes a field or changes what one means, and a client ignores any field it does not know. That way an older client keeps working against a newer service, and a service can say more than this page does without breaking anyone.

A version may also add a value to a list. A client that does not know a stage's state draws it as not_offered, and one that does not know a holder's kind shows the holder's name. Version 0.2 added the roles, evidence, and the states not_bound and not_applicable. Version 0.3 added the stages calls, the build's lifecycle, and the state not_used, which a 0.2 client draws as not_offered.

The schema and a check are open, beside the stages.

The schema, lifecycle-api.schema.json, holds every request and answer above as JSON Schema. It sits in CommonAgent/adlc beside stages.json, under Apache-2.0.

The check, lifecycle-api-check.mjs, reads a running service with a key and says whether its answers keep the contract. It only reads. It checks every answer against the schema, and the rules a schema cannot say: every stage listed once, actions only at stages the build offers, rounds newest first, every role listed once with the requester held by a person, every stage in the stages answer once and in order, a stage the service cannot leave out saying why and kept in use, and a not_used stage with no holder and no runs.

against your own service
$ node standards/lifecycle-api-check.mjs https://your-service.example/v1/lifecycle/ --key-file ./key

It needs Node 22 and nothing else. It takes the key from a file or from ADLC_API_KEY, never from the command line, and never prints it. Exit 0 means the service keeps the contract.

AgentMesh is the first implementation.

AgentMesh answers this API for the agents a person builds there. A person makes a key for their own account on its Keys page and gives it to the client. Any other service that runs the lifecycle can answer the same paths, and the same client will follow its builds too. See Implementations for what holds each stage today.
