The family of standards

Any service that runs the lifecycle answers the same API.

A person may build agents on more than one service, and should be able to follow every build in one place. So a service that implements the lifecycle reports each build stage by stage, in one shape, and says what the person may do next. A client shows what the service says and holds no lifecycle logic of its own.

The schema: lifecycle-api.schema.json · The check: lifecycle-api-check.mjs · Version 0.1

Every service answers these paths.

They sit under /v1/lifecycle on the service. Every request and answer is JSON, and every time is ISO 8601 with a zone.

CallWhat it answers
GET /mewho the key belongs to, { account: { email, name } }, and the service's name, { service: { name } }
GET /buildsthe person's builds, each with its id, name, what it does, its version, the stage it is at and its state there, and when it last changed
POST /buildsa new build, started from the person's words: does, and if they like refuses, more, name and a prototype repository
GET /builds/{id}one build, stage by stage, with its log and the actions it offers now
GET /builds/{id}/files?path=the bytes of a file a stage handed back, at the link the build gives
POST /builds/{id}/actions/{name}the build after the person takes one of the actions it offered
POST /builds/{id}/trythe answer to one input, sent to the pull request or to the installed agent
GET /builds/{id}/triesthe tries made on the build, newest first
POST /builds/{id}/tries/{tid}/keepthe try, now kept as a new test in the agent's suite
POST /builds/{id}/tries/{tid}/wrongthe try, now sent back to whoever holds the code

The person's own key signs every call.

Each call carries Authorization: Bearer <key>. The key is one the person makes for their own account, and the service says how to make one and what it must allow. A client asks for the key once and never sees a password. It sends the key only to the service, and asks for a new one when the service answers 401 or 403.

A build lists all twenty-four stages.

The answer to GET /builds/{id} lists every stage of the lifecycle once, by the ids in stages.json. A stage the service does not run is listed as not_offered, so a client always draws the whole lifecycle and the person can see what this service leaves to someone else.

FieldWhat it says
statenot_started, working, waiting_on_you (the person's act is next), done, refused, stopped or not_offered
holderwho holds the stage: a reference_agent, your_agent (one the person brought) or a person, with a name; null for a stage that is not offered
roundseach time the stage ran, newest first; back is true when that round sent the work back
handed_backwhat the stage handed back, in words and as files, each with its size in bytes and a link read with the same key
done_when_metwhether the stage's "done when" was met: true, false, or null while it is not known
wherewhere the work is when the person can open it, such as a pull request with its newest commit and its check; otherwise null

Beside the stages, a build carries its id, name, what it does, its version, the handle it answers at once installed, its own log, its actions, and can_try, which says whether a try may be sent now to the pull request and to the installed agent.

A client draws one button for each action, and nothing else.

Every build carries the actions the person may take now. A client shows each one as a button with its label, asks for the inputs it needs, and posts them to /builds/{id}/actions/{name}. It never adds a button the service did not offer and never decides on its own what comes next, so every judgment stays with the service and its agents. When the service offers nothing, the person has nothing to do.

an action, as the build offers it
{
  "stage": "requirements",
  "name": "approve",
  "label": "Approve the spec",
  "needs": [
    { "name": "repository",
      "label": "Your coding agent's repository, as owner/name",
      "kind": "repository",
      "optional": true }
  ]
}

A need's kind is text for a line, words for a paragraph, or repository for owner/name. A need marked optional may be left empty, and is then not sent. An action names the stage it acts at, and that is always a stage the build offers. The answer is the build as it now stands.

Try it, keep what it got right, and send back what it got wrong.

Before the person accepts the code, and after the agent is installed, they can send it one input and read the answer.

  • Try. POST /builds/{id}/try with { say, against }, where against is pull_request or installed. The answer is { try: { id, say, against, answer, ms, at } }. Against the pull request, the service runs the newest commit on that one input, through the same checks its gate uses. Against the installed agent, it sends the agent a message as the person and waits for the reply.
  • Keep. POST /builds/{id}/tries/{tid}/keep adds the try to the agent's suite as a new test file, so the answer it gave becomes one it must keep giving.
  • Wrong. POST /builds/{id}/tries/{tid}/wrong with an optional { why } sends the try back to whoever holds the code, as a comment on the pull request.

GET /builds/{id}/tries lists every try, newest first, each saying whether it was kept and whether it was sent_back. A service may cap how many tries a build has in a day.

An error is words a person can read.

Any refusal is a 4xx or 5xx status with { error } in words, which a client shows as they are. A refused action also carries the build as it now stands. A 401 or 403 means the key is missing, wrong, or does not allow the call. A 429 means the service was asked too often, and a client waits before asking again.

Version 0.1 grows only by adding fields.

This is version 0.1, served on the /v1/lifecycle path. It changes only by adding fields. A service never removes a field or changes what one means, and a client ignores any field it does not know. That way an older client keeps working against a newer service, and a service can say more than this page does without breaking anyone.

The schema and a check are open, beside the stages.

The schema, lifecycle-api.schema.json, holds every request and answer above as JSON Schema. It sits in CommonAgent/adlc beside stages.json, under Apache-2.0.

The check, lifecycle-api-check.mjs, reads a running service with a key and says whether its answers keep the contract. It only reads. It checks every answer against the schema, and the rules a schema cannot say: every stage listed once, actions only at stages the build offers, and rounds newest first.

against your own service
$ node standards/lifecycle-api-check.mjs https://your-service.example/v1/lifecycle/ --key-file ./key

It needs Node 22 and nothing else. It takes the key from a file or from ADLC_API_KEY, never from the command line, and never prints it. Exit 0 means the service keeps the contract.

AgentMesh is the first implementation.

AgentMesh answers this API for the agents a person builds there. A person makes a key for their own account on its Keys page and gives it to the client. Any other service that runs the lifecycle can answer the same paths, and the same client will follow its builds too. See Implementations for what holds each stage today.
