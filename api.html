The family of standards

Any service that runs the lifecycle answers the same API.

A person may build agents on more than one service, and should be able to follow every build in one place. So a service that implements the lifecycle reports each build stage by stage, in one shape, and says what the person may do next. A client shows what the service says and holds no lifecycle logic of its own.

The schema: lifecycle-api.schema.json · The check: lifecycle-api-check.mjs · Version 0.4.5

Every service answers these paths.

They sit under /v1/lifecycle on the service. Every request and answer is JSON, and every time is ISO 8601 with a zone.

CallWhat it answers
GET /mewho the key belongs to, { account: { email, name } }, and the service's name, { service: { name } }
GET /buildsthe person's builds, each with its id, name, what it does, its version, what it makes (kind: agent or process), the stage it is at and its state there, where it ended in words, and when it last changed; archived builds only when the request adds ?archived=1
POST /buildsa new build, started from the person's words: does, and kind when it is a process, and if they like refuses, more, name, a prototype repository and the project it is for
GET /builds/{id}one build, stage by stage, with its log and the actions it offers now
GET /builds/{id}/timelinehow long each step took: one bar per step per round, with who held it, whether an agent was working or it waited on a person or on something outside, its start, end and duration, and the totals
GET /builds/{id}/files?path=the bytes of a file a stage handed back, at the link the build gives
POST /builds/{id}/actions/{name}the build after the person takes one of the actions it offered; from 0.4.4 it also takes a product's when-needed action, and the answer then adds its result
POST /builds/{id}/trythe answer to one input, sent to the pull request or to the installed agent
GET /builds/{id}/triesthe tries made on the build, newest first
POST /builds/{id}/tries/{tid}/keepthe try, now kept as a new test in the agent's suite
POST /builds/{id}/tries/{tid}/wrongthe try, now sent back to whoever holds the code
POST /builds/{id}/evidencethe build, after a holder outside the service hands back evidence for a stage in one of the open formats

GET /productsevery product, each with its newest build and its versions; a product whose builds are all archived only when the request adds ?archived=1
GET /products/{name}one product: its builds, newest first, the run plan of its newest build that has one, a short activity feed, its setup and when-needed lists, the version that runs, and whether it is retired

The person's own key signs every call.

Each call carries Authorization: Bearer <key>. The key is one the person makes for their own account, and the service says how to make one and what it must allow. A client asks for the key once and never sees a password. It sends the key only to the service, and asks for a new one when the service answers 401 or 403.

A build lists all twenty-five stages.

The answer to GET /builds/{id} lists every stage of the lifecycle once, from Reverse engineering, numbered 00, to Decommission, by the ids in stages.json. A stage the service does not run is listed as not_offered, so a client always draws the whole lifecycle and the person can see what this service leaves to someone else.

FieldWhat it says
statenot_started, working, waiting_on_you (the person's act is next), done, refused, stopped, not_offered (this service cannot hand the stage to anyone), not_bound (nobody holds its role), not_applicable (it does not apply to this kind of build, such as Review on a process) or not_used (the build's lifecycle leaves it out)
holderwho holds the stage: a reference_agent (the service's own), your_agent (one the organization brought), a contracted supplier's agent, a person or an outside_tool, with a name, and a handle when it is an agent on the mesh; null for a stage that is not offered, not bound, not applicable or not used
roundseach time the stage ran, newest first; back is true when that round sent the work back; a round that ran the suite may add by_feature, how many of each feature's tests passed
handed_backwhat the stage handed back, in words and as files, each with its size in bytes and a link read with the same key
done_when_metwhether the stage's "done when" was met: true, false, or null while it is not known
wherewhere the work is when the person can open it, such as a pull request with its newest commit and its check; otherwise null
evidencewhat a holder outside the service handed back for the stage, each piece with its format, name, when it arrived, and what the service read in it, in words
cadencethe stage's cadence in stages.json: every_build, setup or when_needed (see setup and when needed)
carriedon a setup stage whose holder and settings are the same as an earlier version's: the version it has held since, that build's id, and words such as "Unchanged since 0.1.0"
featureshow many of the product's features the stage covers on this build, { covered, total, words }; present on an every-build stage that has made its artifact, when the build carries features (see features)

Beside the stages, a build carries its id, name, what it does, its version, the handle it answers at once installed, its own log, its actions, and can_try, which says whether a try may be sent now to the pull request and to the installed agent. It also carries kind, agent or process, absent meaning agent, and a service that does not build the kind asked for refuses the request and says so; summary, where it ended or where it is in the words a person reads first, such as "Installed · conforms" or "Stopped at Requirements"; paused, since when and why the installed agent is paused, for example after a conformance check it failed, or null; archived, true once the person archived it; timeline, the same bars the timeline call answers; project, the project it was started under, when one was named; lifecycle, whose choice of stages it started under and when, { project, at }, with project null when the build named none; and artifacts, what the build has made and will make, in stage order, only for the stages its lifecycle uses (see a stage's workspace).

An organization chooses which stages its lifecycle uses.

Not every organization runs all twenty-five stages. It can leave a stage out for the whole organization, or for one project, and a project's choice wins for builds started under that project. When nothing is chosen, every stage is used. GET /stages lists every stage in the order of stages.json, each saying whether it is used, where that choice comes from, and whether this service can run its builds without it.

FieldWhat it says
projectthe project asked about, or null for the organization
usedwhether the lifecycle uses the stage
fromwhere the choice comes from: project, org, or default, which uses every stage
can_leave_outwhether this service can run its builds without the stage; a fact about the service, not a rule of the organization's

updated_atwhen a choice this answer reads was last changed; absent when nobody has chosen

PUT /stages/{stage} with { used } makes the choice, and DELETE /stages/{stage} removes it; either takes ?project= for one project, and both answer with the stages as they now stand. The service answers 400 for a stage stages.json does not name, or for used: false on a stage it cannot build without; 403 for a member who is not an admin of the organization; and 409 when the choice could not be saved.

A build keeps the choice in effect when it started. Leaving a stage out later changes the builds started later, never one already running. Each stage the build leaves out is listed as not_used, with no holder, no runs and no actions, and its given says whose choice it was. When a stage both does not apply to the kind of build and is left out, it reads not_applicable; otherwise not_used comes before every other state.

An organization chooses who holds each role.

Each stage is held by one or more roles, the ones written down at agentroles.ai. GET /roles lists every role in stages.json with its contract, the offering an agent holding it answers (role-<id>), its stages, the binding in effect, and where that comes from: project, org, default (the service's own agent) or unbound. PUT /roles/{role} with { holder } binds a role, and DELETE /roles/{role} removes the binding; either takes ?project=. The requester, who holds Acceptance, is always the person who asked.

PUT /roles/{role} answers 400 for a role stages.json does not name, a your_agent or contracted holder with no handle, the requester bound to anyone but a person, or an evidence format stages.json does not list. A binding carries the holder and, unless it is the default, its scope ({ "org": true } or { "project": name }), since and by.

An agent bound to a role is sent the stage's input under the role's offering, and its answer is the stage's asset, as the service's own agent's would be. The service never calls a vendor's API. A holder outside the mesh hands its evidence back with POST /builds/{id}/evidence in an open format stages.json lists: SARIF, CycloneDX, SPDX, SLSA provenance, in-toto, OpenTelemetry traces with gen_ai attributes, or Pact. The service reads it and shows it on the stage, and answers 400 when the content does not read as the format named.

A client draws one button for each action, and nothing else.

Every build carries the actions the person may take now. A client shows each one as a button with its label, asks for the inputs it needs, and posts them to /builds/{id}/actions/{name}. It never adds a button the service did not offer and never decides on its own what comes next, so every judgment stays with the service and its agents. When the service offers nothing, the person has nothing to do.

an action, as the build offers it
{
  "stage": "requirements",
  "name": "approve",
  "label": "Approve the spec",
  "needs": [
    { "name": "repository",
      "label": "Your coding agent's repository, as owner/name",
      "kind": "repository",
      "optional": true }
  ]
}

A need's kind is text for a line, words for a paragraph, repository for owner/name, or, from 0.4.4, choice, one of its options. A need may carry a default, filled in before the person changes it. A need marked optional may be left empty, and is then not sent. An action names the stage it acts at, and that is always a stage the build offers. The answer is the build as it now stands.

Try it, keep what it got right, and send back what it got wrong.

Before the person accepts the code, and after the agent is installed, they can send it one input and read the answer.

  • Try. POST /builds/{id}/try with { say, against }, where against is pull_request or installed. The answer is { try: { id, say, against, answer, ms, at } }. Against the pull request, the service runs the newest commit on that one input, through the same checks its gate uses. Against the installed agent, it sends the agent a message as the person and waits for the reply.
  • Keep. POST /builds/{id}/tries/{tid}/keep adds the try to the agent's suite as a new test file, so the answer it gave becomes one it must keep giving.
  • Wrong. POST /builds/{id}/tries/{tid}/wrong with an optional { why } sends the try back to whoever holds the code, as a comment on the pull request.

GET /builds/{id}/tries lists every try, newest first, each saying whether it was kept and whether it was sent_back. A service may cap how many tries a build has in a day.

Every build of one name is a product.

A product is every build of one name, one build per version. It is not a project, which is the lifecycle's team scope. GET /products lists each product once, with its newest build (its id, its version, how the build stands as a whole, and the stage it is at) and its versions, newest first. How a build stands as a whole is working, waiting_on_you, refused, stopped or done. GET /products/{name} answers one product, and 404 for a name no build has.

Each stage of a build is a workspace.

GET /builds/{id}/stages/{stage} answers one stage as a workspace: what it was given, as the ids of the earlier stages' artifacts the build made; what it handed back, as its own artifacts; what done means for it, its done_when in stages.json; and its gate. Its state, holder, cadence, carried and features are the same as the build's stage. It answers 404 for a stage stages.json does not name.

FieldWhat it says
giventhe artifacts of earlier stages the stage was given, as ids in the build's artifacts, only those made
outputsthe build's artifacts this stage makes
done_whenwhat done means for the stage, as stages.json says it
gatethe last time the stage waited on a person, or waits now; absent when it never has. state is open or answered; actions are, while it is open, the names of the build's actions at this stage that this person may take now, so its buttons are the build's; answered says who answered it, when, and with which action; closed says why it closed without an answer, such as a newer push to the pull request; who_may says who may answer it. At Requirements it also carries open, what the statement still leaves open for the person, and features (see features)

An artifact is something the build has made or will make, one per stage output. Each has an id unique within its build, such as statement or suite; the stage that makes it; its name as a person reads it; by, the holder's name; and, once made, its version (such as "v4" or a short commit), its digest as sha256:<hex> when it has one, when it was made, and its files, at links read with the same key. Its state is made; next, the next one the build will make; later; not_made, when its stage ran or the build ended without it; or not_run, when its stage is in the lifecycle and the service does not run it. Its summary says what it says, readable and never raw file content, in the shape its kind names:

KindIts summary
statementthe agent's name and version, its offerings (each with a name and what it does), what it refuses, what it records, its price, the questions the spec writer left open, and from 0.4.3 its features
suitethe count of tests and each test's name, as written
programsthe scripts Code wrote, each with its path, lines and what it says it does; the commit; and the pull request they were written on
findingsthe code critic's findings still open, each with its place, claim and consequence; its verdict; and notes outside the change, which hold nothing up
securitywhat the agent may reach, what it may spend, what it must never do, and the verdict
packagethe package file, its digest, and whether it validated
run_planfor each stage after Package, who holds it, the holder's settings in words, and how it reads
architecture, build_record, attestation, agentdoc, other, or any artifact not made{ words }: what it is, or why it is not there. A client that does not know a kind reads summary.words, or the name

Each stage has a chat with the agent that holds it.

GET /products/{name}/stages/{stage}/messages answers the chat, oldest first. It is kept per product per stage, across the product's builds, and each message names the build and the version it was said in. A gate is not a message: it is on the stage's workspace. POST to the same path with { text }, and if they like the build it is about (the product's newest when absent), says something to the agent. The agent answers in words from the stage's outputs, what it was given and the build's record, and the person's message and the reply are both kept. Anyone who may read the build may post.

Answering changes nothing. When the person asks for a change, the reply proposes the build's existing action for it with its needs filled, and only when the person may take that action now. The person takes it with the actions operation, so a change always goes back through its gate.

FieldWhat it says

Posting answers 400 in words for a stage the build's lifecycle leaves out, or one held by a person, an outside tool or anyone the service cannot send messages to; and 409 when no agent can answer now, such as when the model is not set.

The product's boss answers for the whole product.

The boss holds the boss role: a conversation at the product level with an agent that answers from the product's record. It routes a directive into the chat of the stage that owns it and says where it went; breaks a larger request into a plan, naming each stage in order and the gate the person meets at each; and proposes the first stage's existing action, or first the start of the next version when the request changes the agent's statement. It never answers a gate, never changes an artifact, and takes no action itself. A stage's action is taken with the actions operation, and the next version starts only when the person confirms that proposal to the boss.

GET /products/{name}/boss/messages answers the conversation, oldest first, each message naming the product's newest build and its version when it was said. POST to the same path with { text }, and with confirms or declines naming an open proposal when the person answers one, says something to the boss. Anyone who may read the product may post, and a proposal of a gate's action is made only to a person who may answer that gate.

routedwhere the boss posted a directive: the stage's chat, the message it posted there, and the build
planthe stages a larger request touches, in the order the lifecycle runs them, each with what it must do and the gate the person meets there, when it has one
proposeswhat the boss proposes: one of the build's existing actions with its needs, or start_version, which asks to start the product's next version with that build as its prototype; when says when the build will offer an action it does not offer yet; state is open, taken, declined or closed
startedthe build the boss started, only on the person's confirmation of a start_version proposal
droppedeach stage the boss told that withdrawn work is no longer wanted, with the message it posted there
confirms, declineson a person's message: the proposal it answered
featuresthe new or changed features the boss proposes in this reply

GET /products/{name}/boss/commitments lists everything the boss committed on the person's behalf, oldest first, in full and never a selection. Each commitment says its kind (routed, a directive posted into a stage's chat; proposed, a proposal made to the person; started, a build started on the person's confirmation; or dropped, a stage told that work is no longer wanted), whom it was to, what, the build and version, and the boss's reply it was made in. A route or a drop names the message posted in the stage's chat, a drop names the commitment it withdraws, a proposal carries the person's answer, and a started build carries the confirmation it was started on.

Posting answers 400 in words for an empty message or a proposal that is not open, and 409 when the boss cannot answer now, such as when the model is not set. A service that does not offer the boss answers its calls 404.

Some stages run on every build, some are set up once, and some run when needed.

Each stage has a cadence in stages.json, and the build's stages and the stage workspace carry it. every_build is the routine, run on every build: Requirements, Test, Code, Review, Security review, Package, Release, Deploy, Conformance, Acceptance and Docs. setup is set up once per product and carried forward to each later version until someone changes it: Architecture and Design, Source, Publish, Monitor, Eval, Incident response, Cost and Update. when_needed is an action on the product, run when something happens, not as part of a build: Reverse engineering, Impact, Retract, Reconfigure, Rollback and Decommission. A client shows a build's steps from its every-build stages, and the others on the product.

A product's setup list holds each setup stage once, as the product's lifecycle has it now: the lifecycle of the project its newest build was started under, or the organization's. Each item names the stage, the role whose holder holds it, the project (null for the organization's), its state (chosen, not_chosen, so the stage is for the person to set up, or not_used), the holder, its settings, since, the version it has held since (null when no build has used this choice yet, so it holds from the next version), and words a person reads. From 0.4.4 it also carries a form: the question "Ask the boss" sends for the stage, the role's reference agent when it has one (a client offers it as a holder only then), a few fields, each a number, text or choice with a label, a default and, as it fits, a unit, options, a least and a most, and shares, words saying one holder holds two stages, each with its own settings.

one item of a product's setup list
{
  "stage": "monitor",
  "name": "Monitor",
  "role": "watcher",
  "project": null,
  "state": "chosen",
  "holder": { "kind": "your_agent", "name": "Our watcher",
              "handle": "watcher.you@example.com" },
  "settings": { "every_minutes": 5, "alert_where": "the console" },
  "since": "0.1.0",
  "words": "Unchanged since 0.1.0",
  "form": {
    "ask": "Who should monitor word-tally?",
    "reference_agent": "watcher",
    "fields": [
      { "name": "every_minutes", "label": "Check every",
        "kind": "number", "unit": "minutes", "default": 5, "min": 1 },
      { "name": "alert_where", "label": "Alert where",
        "kind": "text", "default": "the console" }
    ],
    "shares": "The watcher holds Monitor and Cost: one holder for both, each with its own settings."

A form is saved with PUT /roles/{role}: the holder chosen, with each stage's values under that stage's id in the holder's settings, such as { "monitor": { "every_minutes": 5 }, "cost": { "monthly_ceiling": 50 } }, beside any other stage the same role holds. Settings never hold a key or any other secret. When the holder keeps settings under a stage's id, the setup item's settings are that entry.

A product's when_needed list holds each when-needed stage once, in order. can_run says whether the service can run it on the product now; when it cannot, why_not says why, and a client draws the button disabled with those words. When it can, the item names the action that runs it (the build, the action's name and label, and from 0.4.4 its needs) and a confirm card. Its last is the last time it ran on the product, done or refused: when, by whom, whether it was ok, in words, on which build and version, and the files it handed back, such as the impact report.

one item of a product's when-needed list
{
  "stage": "rollback",
  "name": "Rollback",
  "can_run": true,
  "action": {
    "build": "b2", "name": "rollback", "label": "Roll back",
    "needs": [
      { "name": "to_version", "label": "Go back to",
        "kind": "choice", "options": ["0.1.0"], "default": "0.1.0" },
      { "name": "why", "label": "Why", "kind": "words" }
    ]
  },
  "confirm": {
    "title": "Roll back word-tally to 0.1.0?",
    "will": "the agent back on that version, why, and what can't be undone",
    "done_when": "it answers on the old version, and the side effects are named",
    "steps": ["Your runtime puts word-tally back on 0.1.0."],
    "who_may": "Only Ana Lee (ana@example.com) may roll back word-tally.",
    "you_may": true,
    "from_version": "0.2.0",
    "to_version": "0.1.0",
    "cannot_undo": ["What word-tally 0.2.0 did while it ran stays done."]
  }
}

The confirm card is what a person reads before the action runs. title asks the question; will and done_when are the stage's own words in stages.json; steps say what the service will do for this product now; who_may says who may take it, read as for a gate; you_may says whether the person asking may; from_version is the version it acts on; to_version is, for Rollback, the version it goes back to, and for Impact, the changed version it compares; cannot_undo names what cannot be undone; and for Reconfigure, changes lists each stage whose holder or settings differ from the run plan the running version has. A client shows the card when the button is pressed and takes the action only on the person's confirm. When you_may is false, it shows who_may and does not offer the confirm.

The action is taken with POST /builds/{build}/actions/{name} on the build the item names, where the name is the stage's id: impact, retract, reconfigure, rollback or decommission. The build need not list it among its own actions. The answer is the build with a result: the stage, whether it was ok, what it did in words, and as it fits cannot_undo (for Rollback), the files it handed back, and the report (for Impact, the impact analyst's report as Markdown). The product keeps the result as the item's last. The service answers 403 in words to a person the lifecycle does not let take it, 400 for a need left empty, and 409 when it is not offered on that build now, or when the holder it runs through, such as the runtime, refuses, with the holder's words; a refusal is kept on the build like a result. How a service hands rollback, reconfigure and retire to the runtime it is given is in runtime-verbs.md.

Every feature is approved one at a time and followed across the lifecycle.

The statement of the job carries a feature list. Each feature has an id, such as F3, that stays the same across the product's versions and is never given to another feature; a name of a few words; what it does, in one sentence; and the offering of the statement it belongs to. A stage's agent or the boss proposes a new or changed feature in a reply, under features, and the person answers each proposal there, one at a time.

a feature proposal, on a reply
{
  "proposal": "fp1",
  "feature": "F2",
  "name": "Empty passage",
  "does": "Answers 0 for an empty passage.",
  "offering": "Count",
  "change": "new",
  "state": "open",
  "you_may_approve": true,
  "approvers": []
}

A proposal's change is new or changed, and a changed one says what the feature was. Its state is open; asked, waiting on the approvers; approved; not_now, a backlog item; or replaced, when a newer proposal of the same feature came after it. you_may_approve says whether the person reading it may answer the Requirements gate, and approvers who may, empty when anyone may. An answered proposal says who answered it, when and how; an asked one says who asked whom, and when.

  • Approve. POST /builds/{id}/features/{feature}/approve with { proposal }, and the message it was answered on when it was in a chat. It is a gate decision of Requirements for that feature alone, recorded with who gave it and when, and the statement of the job gets a new version with the feature in it. Only a person who may answer the Requirements gate may approve; anyone else gets 403 in words, and asks instead. It answers 400 in words for a proposal that is not open.
  • Not now. POST /builds/{id}/features/{feature}/not_now leaves it for later: it stays proposed, as a backlog item linked to the conversation it came from. Anyone who may read the build may say not now.
  • Ask. POST /builds/{id}/features/{feature}/ask asks the people who may answer the Requirements gate. Each is told through the service's notices and sees the same proposal, with its approve button.

Each answers with the feature as the product now holds it (approved or proposed, whether it is in the backlog, its newest approval, and the proposal still waiting, when one is), the proposal as the person now sees it, the statement's new version after an approval, and who was told after an ask.

A test names the feature it checks by starting with the feature's id in square brackets, such as "[F3] counts an empty passage as none". A round of the gate that ran the suite reports its results per feature, by_feature. The Requirements gate carries features: those already approved in a chat, which are not asked about again; those to_approve, which approving the gate approves; and the backlog, which stays proposed.

GET /builds/{id}/features answers the build's features as a matrix, and GET /products/{name}/features the product's, for its newest build or with ?version= for another. The answer names the product, the build and its version, the product's versions for a version filter, the columns in the order spec, tests, code, review, docs, and one row per feature.

one row of the features matrix
{
  "id": "F1",
  "name": "Count words",
  "does": "Counts the words in a passage.",
  "offering": "Count",
  "state": "approved",
  "backlog": false,
  "badge": "unchanged",
  "cells": {
    "spec": { "state": "done", "words": "Spec v3",
      "link": { "build": "b2", "stage": "requirements",
                "artifact": "statement", "feature": "F1" } },
    "tests": { "state": "done", "words": "Tests 2/2",
      "tests": { "passed": 2, "total": 2 } },
    "code": { "state": "done", "words": "Passes 2/2",
      "tests": { "passed": 2, "total": 2 } },
    "review": { "state": "done", "words": "No findings" },
    "docs": { "state": "missing", "words": "No docs yet" }
  },
  "tests": ["[F1] counts the words", "[F1] counts a hyphenated word once"],
  "from": { "build": "b1", "stage": "requirements", "message": "t2" }
}
FieldWhat it says
stateapproved, approved at least once, or proposed, never approved yet; backlog is true when its newest proposal was left for later
badgeagainst the product's version before this one: new when it was not approved there, changed when its name, what it does or its offering differ, unchanged otherwise
cellsone per column, each done (the artifact covers the feature as approved), stale (it covers an older version of the feature, or was made before an artifact it depends on changed), missing or failing (tests naming the feature fail), with short words, the tests and how many passed for tests and code, and a link that opens the artifact at this feature
pendingthe proposal waiting for an answer, as the person reading it sees it, so a client can answer it beside the list
fromwhere its newest proposal was said: the message, in the chat of the stage named, or the boss's when none is
teststhe tests in this build's suite that check it: those whose names start with its id, and those mapped to it when the features were listed after the build

Beside the rows, the matrix carries words saying how features are added when there are none, unmapped, the tests in the suite that check no feature, and backfill, whether the product's features can be listed from its statement of the job now and, in words, what that does or why not. GET /products/{name}/features/{feature} answers one feature and its history, oldest first: proposed, approved, not_now and asked for its proposals and their answers, and spec, tests, code, review and docs when an artifact that covers it was made or changed, each entry linked to the message or the artifact. It answers 404 for a feature the product does not have.

Since 0.4.5, each every-build stage shows its features. On the build, the stage's features is a short count. covered is, at Requirements, the features approved; at Test, the approved features with a test; at Code, those whose tests all pass; at Review, those with no open finding tied to them; and at Docs, those the docs name. total is, at Requirements, the features proposed or approved, leaving out those only in the backlog, and at every other stage the approved features. On the stage's workspace, features lists them one line each: every feature at Requirements, each approved feature elsewhere. A line's state is done, to_do (such as a feature with no test), failing, stale or findings (Review has open findings tied to it), with short words; at Test, the tests that check it; at Code, how many passed of its tests; at Review, the findings tied to it through its tests. At Test and Review, untied lists the tests that check no feature, or the findings tied to none. They are shown as not tied to a feature, never guessed.

A product made before features existed can have them listed. POST /builds/{id}/features/backfill with {} sends the person's message to the spec writer, in the Requirements chat, and answers with the message and the reply, as a chat does. The reply proposes every feature of the statement of the job, each with the tests already in the build that clearly check it; a test whose name or content does not make that clear is left out, never guessed. It answers 409 in words when it is not offered, and the matrix's backfill says why. POST /builds/{id}/features/approve_all with { proposals }, at least one, and the message when it was in a chat, approves several at once: each a recorded gate decision of Requirements, together one new version of the statement of the job. It answers with the proposals approved, each feature after the answer, and the statement's new version. Only a person who may answer the Requirements gate may; anyone else gets 403 in words. It answers 400 in words, approving none, when any proposal is not open.

A service that does not offer features answers their calls 404.

An error is words a person can read.

Any refusal is a 4xx or 5xx status with { error } in words, which a client shows as they are. A refused action also carries the build as it now stands. A 401 or 403 means the key is missing, wrong, or does not allow the call. A 429 means the service was asked too often, and a client waits before asking again; a 429 from a try also says tries_today and tries_cap.

Version 0.4.5 grows only by adding.

This is version 0.4.5, served on the /v1/lifecycle path. It changes only by adding. A service never removes a field or changes what one means, and a client ignores any field it does not know. That way an older client keeps working against a newer service, and a service can say more than this page does without breaking anyone.

A version may also add a value to a list. A client that does not know a stage's state draws it as not_offered, and one that does not know a holder's kind shows the holder's name. Each version added these, as the changelog records:

  • 0.2: the roles, evidence, and the states not_bound and not_applicable.
  • 0.3: the stages calls, the build's lifecycle, and the state not_used, which a 0.2 client draws as not_offered.
  • 0.4: products, stage workspaces, each stage's chat, and the build's artifacts. A 0.3 client ignores artifacts, and a service that does not offer these calls answers them 404.
  • 0.4.1: the product's boss. A service that does not offer it answers its calls 404.
  • 0.4.2: each stage's cadence and carried on the build and the stage workspace, and a product's setup and when_needed lists.
  • 0.4.3: features: the statement's feature list, feature proposals on a stage's or the boss's reply, answered with approve, not now or ask, a round's by_feature, the Requirements gate's open and features, the features matrix per build and per product version, and each feature's history.
  • 0.4.4: the guided setup and the when-needed actions: a setup item's form, a when-needed item's needs, confirm card and last run, a choice need with options and default, the actions call's result, and the product's running and retired.
  • 0.4.5: features at every stage: each every-build stage's count on the build and its list on the workspace, a matrix row's pending, from and tests, the matrix's unmapped tests and backfill, a proposal's tests, and the backfill and approve-all calls.

The schema and a check are open, beside the stages.

The schema, lifecycle-api.schema.json, holds every request and answer above as JSON Schema. It sits in CommonAgent/adlc beside stages.json, under Apache-2.0.

The check, lifecycle-api-check.mjs, reads a running service with a key and says whether its answers keep the contract. It only reads. It checks every answer against the schema, and the rules a schema cannot say: every stage listed once, actions only at stages the build offers, rounds newest first, every role listed once with the requester held by a person, every stage in the stages answer once and in order, a stage the service cannot leave out saying why and kept in use, a not_used stage with no holder and no runs, and a stage's cadence the one stages.json gives it, with carried only on a setup stage.

Against a running service it reads the calls up to 0.3, so a service that does not offer 0.4 still passes. The answers added since are checked by functions it exports, which a service's own tests and a client call: checkProducts, checkProduct, checkStageWorkspace, checkMessages, checkMessageReply, checkBossMessages, checkBossReply, checkBossCommitments, checkFeatures, checkFeature, checkFeatureDecision and checkFeatureApproveAll. Their rules include: an artifact's summary has its kind's shape; a workspace's outputs are its own stage's, and what it was given was made; an open gate's buttons are the build's; a chat is oldest first and a proposal names an action the build offers now; a boss's plan is in the lifecycle's order, and a build is started only on a confirmation; setup and when_needed list every such stage once, in order; only an item that can run has a confirm card, and a rollback's card names the version it goes back to and what cannot be undone; a retired product runs nothing; a matrix's columns are in order, with each feature once; a stage never covers more features than it has; and approve_all lists every proposal it was asked to approve.

against your own service
$ node standards/lifecycle-api-check.mjs https://your-service.example/v1/lifecycle/ --key-file ./key

It needs Node 22 and nothing else. It takes the key from a file or from ADLC_API_KEY, never from the command line, and never prints it. Exit 0 means the service keeps the contract.

AgentMesh is the first implementation.

AgentMesh answers this API for the agents a person builds there. A person makes a key for their own account on its Keys page and gives it to the client. Any other service that runs the lifecycle can answer the same paths, and the same client will follow its builds too. See Implementations for what holds each stage today.
